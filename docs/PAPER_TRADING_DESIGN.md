# Paper Trading Design

This is design only. No paper trading engine is implemented in this document or this task.

---

## Purpose

Define a safe, offline-first paper trading architecture for HQE before any fake execution
or paper-trading state code is written.

Paper trading is the phase between offline backtesting and real-money execution.
It allows HQE to consume live or replayed market data, generate option-buy trade plans
from the existing planning pipeline, and record fake paper orders and positions locally —
without placing real orders, without connecting to a broker, and without risking capital.

---

## Current Status

HQE currently has:

- Offline option market data recording workflow (record -> validate -> replay).
- Option-buy backtest pipeline (snapshot loader, premium candle loader, scenario builder,
  backtest runner).
- Backtest-readiness smoke test proving demo CSVs flow through existing loaders.

Paper trading is not yet implemented. This document plans the next phase.

---

This design document does not:

- Implement any paper trading engine.

- Place paper orders (paper order execution is a future implementation task).
- Make profitability claims.
- Allow option selling.
- Allow short CE or short PE positions.
- Allow futures or equity execution.

Real-money execution remains the last phase and must be isolated from core logic.

## Proposed Safe Architecture

```
TradeSignal
    |
    v
OptionBuyTradePlan
    |
    v
PaperOrderRequest
    |
    v
PaperOrderJournal
    |
    v
PaperPositionState
    |
    v
PaperTradingReport
```

Each layer is broker-agnostic. No broker SDK is imported by any layer in this chain.

---

## Paper Trading Flow

1. A `TradeSignal` is generated by the existing HQE strategy pipeline from NIFTY
   spot/index candle data.

2. Signal direction determines option type:
   - `LONG` signal -> CE buy plan (Call option buy only).
   - `SHORT` signal -> PE buy plan (Put option buy only).
   - `NEUTRAL` signal -> no paper trade is created.

3. The existing `OptionBuyPlanner` consumes the signal and an `OptionChainSnapshot`
   to produce an `OptionBuyTradePlan`.

4. The `OptionBuyTradePlan` is passed to a future `PaperOrderRequest` builder that
   wraps the plan in a fake order record.

5. The `PaperOrderRequest` is written to a `PaperOrderJournal` (local CSV or in-memory
   store). No broker API is called.

6. `PaperPositionState` tracks open and closed paper positions from the journal.

7. `PaperTradingReport` reads the journal and position state to produce a daily summary.

Rules that must hold throughout:

- No option selling.
- No short CE or short PE.
- No futures execution.
- No equity execution.
- No real orders.
- No broker credentials required.

## Paper Order Journal

The `PaperOrderJournal` is a local record of fake paper orders.

Proposed fields per record:

- `order_id` — unique fake order identifier.
- `timestamp` — time the paper order was created.
- `signal_type` — LONG or SHORT.
- `option_symbol` — option contract symbol (e.g. NIFTY_24200CE).
- `option_type` — CE or PE.
- `strike_price` — selected strike.
- `expiry_date` — contract expiry.
- `entry_price` — paper entry premium.
- `stop_loss` — paper stop loss level.
- `target` — paper target level.
- `lot_size` — contract lot size.
- `quantity` — number of lots.
- `status` — OPEN, CLOSED_TP, CLOSED_SL, CLOSED_MANUAL.
- `exit_price` — paper exit premium (blank until closed).
- `exit_timestamp` — time of paper exit (blank until closed).
- `paper_pnl` — fake PnL after paper exit (blank until closed).

Output path: `data/paper_trading/paper_orders.csv`

This path is generated output and must stay gitignored under `data/paper_trading/`.

---

## Paper Position State

`PaperPositionState` tracks which paper orders are currently open.

Responsibilities:

- Load open orders from the journal.
- Update order status when a paper exit condition is met (TP, SL, or manual).
- Prevent duplicate open positions for the same symbol.
- Enforce risk controls before accepting a new paper order.

This is local state only. No broker position query is made.

---

## Paper Risk Controls

Risk controls must be enforced before any paper order is accepted and before any future
live execution is attempted.

Required controls:

- `max_trades_per_day` — maximum number of paper trades allowed per calendar day.
- `max_daily_loss` — maximum cumulative paper loss allowed per day before trading stops.
- `max_position_size` — maximum number of open paper positions at any time.
- `cooldown` — minimum time between paper trades after a stop-loss exit.
- `kill_switch` — manual flag that halts all new paper orders immediately.

These controls must be checked before each `PaperOrderRequest` is accepted into the
journal. If any control is breached, the request is rejected and logged.

---

## Data Sources

Paper trading should use validated and replayed offline data first.

Supported data paths (in order of safety):

1. Replayed CSV data via `CsvReplayOptionMarketDataSource` — safest, fully offline,
   no broker required.
2. Validated recorded CSV data via `OptionChainSnapshotCsvLoader` and
   `OptionPremiumCandleCsvLoader` — offline, broker-agnostic.
3. Future: live broker data via a broker adapter implementing `OptionMarketDataSource`
   — this is a future phase and must stay isolated from core paper trading logic.

Paper trading must not require a live broker connection to function.

---

## Reports

`PaperTradingReport` should produce:

- Total paper trades taken.
- Win rate (paper TP hits / total closed trades).
- Paper gross PnL.
- Estimated charges (using existing `TransactionCostCalculator`).
- Paper net PnL after charges.
- Max paper drawdown.
- Daily paper trade summary.

Output path: `data/paper_trading/paper_trading_report.txt`

Reports must show truth. No fake profit claims. Charges must always be included.

---

## Testing Strategy

All paper trading components must have tests before implementation is considered complete.

Test requirements:

- Unit tests for `PaperOrderRequest` builder.
- Unit tests for `PaperOrderJournal` (write, read, update status).
- Unit tests for `PaperPositionState` (open/close tracking, duplicate prevention).
- Unit tests for each risk control (max trades, max loss, max size, cooldown, kill switch).
- Unit tests for `PaperTradingReport` (summary calculations).
- Integration smoke test: replayed CSV data -> signal -> plan -> paper order -> journal.
- No test may place real orders.
- No test may import broker SDK.
- No test may use live or real market data.
- All tests must use `tmp_path` for any file output.

---

## Future Broker / Live Execution Boundary

The boundary between paper trading and live execution must be explicit and enforced.

Rules:

- Broker-specific code must never enter core paper trading logic.
- A future broker adapter must implement a common `OrderExecutionProvider` interface.
- The paper trading engine must be switchable to live execution only by swapping the
  execution provider — not by changing core logic.
- Live execution requires passing all paper trading risk controls first.
- Live execution requires a minimum paper trading forward-test period (at least one month).
- Real-money execution remains the last phase.
- No milestone is complete unless tests pass and Git is clean.
